# 消费管家 PRD（含 UI/UX）方案

日期：2026-05-26  
状态：校准版草案  
范围：PRD、信息架构、核心流程、UI/UX 设计稿  
依据：0.2.1 变更记录、当前代码变更、已有核心测试结果

## 1. 校准结论

上一版规划的大方向是对的：导入要先进入复核、报告要成为独立能力、手动记账要能反哺规则、核心逻辑要补测试。但它在信息架构和 OCR 策略上判断偏重“功能露出”，没有充分尊重 0.2.1 暴露出的真实问题：入口太多、总览太重、报告和洞察重复、OCR 策略把技术约束暴露给了用户。

校准后的产品策略是：

- 总览只回答“我现在花了多少、有没有异常、要不要手动补一笔”。
- 导入只负责“拿到候选、识别、去重、复核、入账”。
- 报告只负责“总结、洞察、周期归档、历史回看”。
- 我的只负责“隐私边界、提醒、账户、版本与基础设置”。
- OCR 不再作为用户要理解的技术选项，而是产品内部的质量策略：优先使用高质量识别，失败后本机兜底；对用户只解释“是否上传、上传什么、如何关闭”。

## 2. 0.2.1 变更复盘

### 2.1 已经证明的正确方向

1. 信息架构需要减负。
   - 0.2.1 移除了总览里的“导入截图 / 粘贴通知”快捷入口，只保留“记一笔”。
   - 这说明底部已经有“导入”主入口后，总览不应重复承担导入工作流。

2. 报告必须从总览中分离。
   - 0.2.1 将“消费洞察 / 消费总结”归入“报告”页。
   - 这说明总览不适合承载历史解释和长文本分析，否则会和报告页竞争注意力。

3. OCR 策略需要产品化。
   - 0.2.1 将策略改成腾讯 OCR 优先、本机 Vision 兜底，并移除面向用户的“云端 OCR 开关”技术表达。
   - 这说明用户要的是稳定识别和清晰隐私说明，不是选择供应商。

4. 导入复核是正确主线。
   - 分享扩展、快捷指令、截图导入都应该产出候选记录，而不是绕过复核直接写入。
   - 后续要补的是队列可见性、深链精确性、失败解释和测试覆盖。

### 2.2 上一版规划需要修正的部分

| 上一版判断 | 0.2.1 后的复盘 | 新结论 |
| --- | --- | --- |
| 总览可以放更多快捷入口和分析模块 | 入口重复会让用户不知道从哪里开始；分析模块会稀释当前状态 | 总览减到当前期状态 + 手动补记 + 最近记录 |
| 报告、洞察可作为总览的一部分渐进增强 | 报告和洞察本质是周期复盘，不是日常监控 | 报告成为独立主 tab，承接总结、归档、提醒 |
| OCR 配置可以作为设置项给用户选择 | 这会把工程策略推给用户，且本机优先不符合真实账单截图质量 | 用户只看隐私与自动识别状态，内部执行高质量优先与本机兜底 |
| 下一步可以快速扩预算图表、分类分析 | 当前最薄弱的是导入候选可靠性与报告可信度 | 先做稳定校准，再进入报告可信化 |
| 数据刷新可在各入口里局部处理 | 接受候选、手动记账、删除记录都会影响报告和提醒 | 继续收敛到统一 mutation service，避免分散副作用 |

## 3. 产品定义

### 3.1 产品定位

消费管家是一个面向个人日常消费的本地优先记账助手。它不追求一开始就做完整财务系统，而是优先解决三个高频痛点：

1. 支付截图、通知文本、分享内容能快速变成可复核的消费记录。
2. 用户能信任每一笔记录的来源、状态和重复判断。
3. 用户能按天、周、月看到清晰的消费总结，而不是在多个页面重复寻找结论。

### 3.2 目标用户

- 每天通过微信、支付宝、银行卡、外卖、网购产生多笔消费的人。
- 愿意花少量时间复核，但不愿意逐笔手动输入的人。
- 关注月度预算、异常消费和周期复盘的人。

### 3.3 核心原则

- 单入口单职责：每个 tab 只做一件主事。
- 先复核后入账：自动化只生成候选，不直接污染账本。
- 解释结果，不解释实现：用户看到“识别成功 / 需要确认 / 可能重复”，不需要看到 OCR 供应商。
- 报告可追溯：报告必须能解释它基于哪些记录生成，避免“看起来像总结，其实会被重建覆盖”。
- 本地优先但不牺牲可用性：敏感账本保存在本地；识别质量需要云端时，用明确隐私说明承接。

## 4. PRD

### 4.1 当前产品目标

0.2.1 后的下一阶段不扩张新大功能，核心目标是把已经确定的方向做扎实：

- 导入队列可见。
- 深链行为明确。
- 报告刷新可信。
- OCR 文案用户化。
- 核心路径有测试覆盖。

### 4.2 关键使用场景

1. 截图导入
   - 用户在系统分享面板把支付截图分享到消费管家。
   - App 打开到“导入”页，并展示刚生成的候选记录。
   - 用户确认、修改或忽略候选。

2. 文本导入
   - 用户粘贴支付通知文本。
   - 系统解析出商户、金额、时间、支付方式和分类候选。
   - 低置信度字段需要明显标记。

3. 手动记一笔
   - 用户在总览点“记一笔”。
   - 保存后记录进入明细，并触发报告与提醒刷新。
   - 手动分类结果可用于后续规则学习。

4. 周期复盘
   - 用户进入“报告”页选择日、周、月。
   - 看到本期总额、主要类别、异常信号、消费总结和历史报告。
   - 可以进入报告详情查看生成依据。

### 4.3 功能需求

#### R1：导入深链明确化

- `awemebilling://review-import` 必须明确进入“导入”页。
- 如存在最近批次，优先展示最近批次候选；否则展示所有待复核候选。
- 无候选时显示空状态和可执行入口，不出现静默跳转。

#### R2：复核队列始终可见

- “导入”页顶部展示待复核数量、最近来源、最后更新时间。
- `importMessage` 不应隐藏全局待复核队列。
- 允许从当前批次切换到全部待复核。

#### R3：写入后副作用统一

- 接受候选、手动新增、删除、编辑记录后统一触发报告与提醒刷新。
- 逐步把分散的 `save`、`rebuildReports`、通知调度收敛到 mutation service。

#### R4：OCR 状态用户化

- 成功：显示“已自动识别，请确认金额和商户”。
- 兜底：显示“截图质量较复杂，已尝试本机识别，请重点核对金额”。
- 失败：显示“未识别出有效消费，请粘贴通知文本或手动记一笔”。
- 设置页只解释隐私边界，不暴露供应商开关。

#### R5：核心测试补齐

- 覆盖 `ImportPipeline.createBatch`、接受候选、忽略候选、重复判断。
- 覆盖 OCR 文本选择策略。
- 覆盖报告刷新不会因单次写入产生重复报告。

#### R6：我的页版本变化简介

- “我的”页必须展示当前版本号，版本号格式为 `0.3`、`0.3.1` 这类纯数字语义版本，不带 `v` 前缀。
- 版本区域展示“本版本变化简介”，用 2-4 条短句说明用户可感知的新增功能、体验改进和重要修复。
- 支持查看“历史版本变化”，至少保留 `0.2.1`、`0.2.2`、`0.3` 及后续版本的功能变化简介。
- 每次按版本迭代规划落地时，发布前必须同步更新 App 构建版本、我的页当前版本号和版本变化简介。
- 版本变化文案面向普通用户，不使用 PRD、pipeline、fixture、upsert 等内部技术词。

### 4.4 非目标

- 当前阶段不做复杂资产负债、投资、发票管理。
- 当前阶段不引入账号云同步。
- 当前阶段不做大屏数据看板或营销式首页。
- 当前阶段不开放 OCR 供应商选择给普通用户。

### 4.5 成功指标

- 分享截图后，用户 1 步进入待复核候选列表。
- 候选记录从生成到入账路径无重复写入。
- 待复核候选不会被提示文案或空状态遮挡。
- 核心测试覆盖导入、OCR 选择、报告刷新、周期计算。
- 新用户在 30 秒内能完成一次“导入或记一笔”。
- “我的”页版本号与当前发布版本一致，版本变化简介能让用户快速理解本次更新。

## 5. 信息架构

```text
Tab 1 总览
  当前周期状态 / 预算进度 / 异常提示 / 记一笔 / 最近记录

Tab 2 明细
  搜索 / 周期筛选 / 分类筛选 / 记录列表 / 编辑 / 删除撤销

Tab 3 导入
  待复核队列 / 截图导入 / 文本导入 / 当前批次 / 历史批次状态

Tab 4 报告
  周期选择 / 本期洞察 / 报告列表 / 报告详情 / 提醒设置

Tab 5 我的
  隐私说明 / 通知总开关 / 数据管理 / 版本变化 / 基础偏好
```

## 6. UI/UX 设计稿

### 6.1 视觉原则

- 金融工具型界面应克制、清晰、可扫描，避免营销式大 hero。
- 颜色以系统背景、文本层级、蓝色主操作、绿色收入/安全、红色异常为主。
- 卡片只用于重复项、数据摘要和可操作对象，不把整个页面包成卡片。
- 关键操作使用系统图标加短文本；风险操作要有撤销或确认。
- 所有金额、日期、状态必须对齐，避免账本类信息跳动。

### 6.2 总览页

目标：回答“当前状态如何，要不要补一笔”。

```text
┌────────────────────────────┐
│ 总览              今天/月  │
│ 本月支出 ¥3,248.60         │
│ 较上期 +12%    预算剩余 42% │
├────────────────────────────┤
│ [记一笔]                   │
├────────────────────────────┤
│ 预算                       │
│ 餐饮  ¥860 / ¥1200   72%   │
│ 交通  ¥210 / ¥500    42%   │
├────────────────────────────┤
│ 最近记录                   │
│ 星巴克     餐饮   ¥36.00   │
│ 地铁       交通   ¥7.00    │
└────────────────────────────┘
```

交互要求：

- 不出现“导入截图 / 粘贴通知 / 消费总结”。
- 有异常时在金额摘要下方显示一行短提示。
- 最近记录点击进入明细详情。
- “记一笔”保存后刷新总览、明细、报告摘要。

### 6.3 导入页

目标：让用户知道“有什么待确认、来自哪里、下一步做什么”。

```text
┌────────────────────────────┐
│ 导入                       │
│ 待复核 3 条 · 最近来自分享截图 │
├────────────────────────────┤
│ [截图] [粘贴文本]           │
├────────────────────────────┤
│ 当前批次                   │
│ 微信支付截图 · 刚刚          │
│ ¥42.80  瑞幸咖啡  餐饮      │
│ [修改] [忽略] [入账]         │
├────────────────────────────┤
│ 全部待复核                 │
│ 2 条来自快捷指令 / 文本粘贴  │
└────────────────────────────┘
```

交互要求：

- 深链进入后直接滚到当前批次或待复核队列。
- 顶部数字始终来自真实待复核数据，不被临时提示文案覆盖。
- 候选卡片显示来源、时间、重复风险、字段置信度。
- 空状态文案只给下一步动作：导入截图、粘贴通知、手动记一笔。

### 6.4 报告页

目标：让用户复盘周期，而不是在总览里读长分析。

```text
┌────────────────────────────┐
│ 报告              日/周/月  │
│ 本周总结                   │
│ 支出 ¥826.30 · 餐饮占 38%   │
├────────────────────────────┤
│ 洞察                       │
│ 餐饮较上周增加 ¥126         │
│ 晚间外卖连续 3 天出现       │
├────────────────────────────┤
│ 历史报告                   │
│ 5月第4周报告      已生成    │
│ 5月第3周报告      已归档    │
├────────────────────────────┤
│ 提醒设置                   │
│ 每周日 21:30 生成周报       │
└────────────────────────────┘
```

交互要求：

- 报告列表点击进入详情。
- 报告详情可回跳明细筛选。
- 提醒设置折叠在报告页内，不作为主信息。
- 报告生成失败时显示可重试状态。

### 6.5 明细页

目标：作为账本的审计轨迹。

```text
┌────────────────────────────┐
│ 明细        搜索            │
│ [今天] [本周] [本月] [自定义] │
│ [全部分类] [全部方式]        │
├────────────────────────────┤
│ 今天                       │
│ 瑞幸咖啡   餐饮  ¥42.80     │
│ 地铁       交通  ¥7.00      │
└────────────────────────────┘
```

交互要求：

- 保留“今天”筛选。
- 删除后出现撤销，不立即让用户失去安全感。
- 编辑保存后刷新报告摘要。

### 6.6 我的页

目标：只承接设置和信任，不承担数据洞察。

```text
┌────────────────────────────┐
│ 我的                       │
│ 隐私与识别                 │
│ 账本保存在本机。截图识别可能 │
│ 使用云端服务以提升准确率。   │
├────────────────────────────┤
│ 通知                       │
│ 周报提醒  开               │
├────────────────────────────┤
│ 数据                       │
│ 导出 / 清理测试数据         │
├────────────────────────────┤
│ 版本                       │
│ 当前版本 0.3                │
│ · 报告详情可追溯            │
│ · 支持历史版本变化回看       │
│ [查看全部版本变化]           │
└────────────────────────────┘
```

交互要求：

- 不出现“腾讯 OCR / Vision”这类技术开关。
- 可以有高级说明入口，但默认文案用用户语言。
- 隐私说明要明确“什么数据可能上传、为什么、如何关闭相关能力”。
- 版本号不带 `v` 前缀，并与 App 构建版本保持一致。
- 版本变化简介优先展示本版本对用户有感的变化，历史版本放入二级页或展开面板。
