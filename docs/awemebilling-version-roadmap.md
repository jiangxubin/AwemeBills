# 消费管家版本迭代方案

日期：2026-05-26  
状态：校准版草案  
范围：版本功能迭代点、改进点、风险、验收标准  
关联产品设计文档：`docs/awemebilling-product-design.md`  
关联技术与回归测试文档：`docs/awemebilling-technical-architecture-regression.md`

## 1. 规划原则

0.2.1 之后的版本规划不再围绕“增加更多入口和模块”推进，而是围绕三条主线收敛：

- 导入可信：任何自动化入口都只生成候选，用户复核后入账。
- 报告可信：报告要可追溯、可复看，不能因为重建逻辑损害历史可信度。
- 体验减负：总览保持轻量，技术细节收进内部实现，用户只看到结果、风险和下一步动作。

## 2. 0.2.2：稳定校准版

周期：2-4 天  
主题：把 0.2.1 的方向做扎实。  
版本目标：导入队列可见、深链明确、写入副作用统一、测试覆盖核心路径。

### 2.1 功能迭代点

1. 深链与导入队列
   - 明确处理 `awemebilling://review-import`。
   - 导入页顶部展示待复核数量。
   - 当前批次和全局待复核都可访问。

2. 候选复核可靠性
   - 修复提示文案遮挡候选队列的问题。
   - 接受、忽略、批量接受后保持列表状态一致。
   - 重复候选显示原因。

3. 写入副作用统一
   - 手动新增、候选入账、编辑、删除走统一刷新路径。
   - 明细删除增加撤销或二次确认。

4. OCR 状态文案
   - 成功、兜底、失败三种状态使用用户语言。
   - 设置页只解释隐私边界，不暴露供应商开关。

5. 测试补齐
   - 导入 pipeline 单测。
   - OCR 选择策略单测。
   - 报告刷新单测。

### 2.2 改进点

- 从“导入成功提示”改成“待复核任务提示”，减少用户误以为已经入账。
- 从“当前批次优先”升级为“当前批次 + 全部待复核”双层队列。
- 从各页面自行刷新报告，逐步收敛到统一 mutation service。
- 从技术 OCR 文案，改成“自动识别 / 本机兜底 / 识别失败”的结果文案。

### 2.3 验收标准

- 从分享扩展进入 App 后，导入页展示候选，不需要用户再找入口。
- 粘贴文本后，即使有提示文案，待复核队列仍可见。
- 接受同一候选不会产生重复记录。
- 手动新增、编辑、删除后，总览和报告摘要能同步更新。
- 核心测试全绿。

## 3. 0.3：报告可信化

周期：1-2 周  
主题：让报告成为可追溯、可复看的正式能力，并让用户在“我的”页清楚理解每次版本变化。  
版本目标：修正报告生成模型，补报告详情页，建立真实样本回归，补齐版本变化展示和发布版本号同步机制。

### 3.1 功能迭代点

1. 报告 upsert 模型
   - 按周期类型、开始时间、结束时间生成唯一键。
   - 重复生成时更新同一报告，不全量删除重建。
   - 保存生成版本、来源记录摘要和生成时间。

2. 报告详情页
   - 展示总结正文、关键洞察、Top 分类、异常记录。
   - 支持从报告跳转到明细筛选。
   - 显示报告状态：已生成、已更新、生成失败。

3. 报告提醒体验
   - 折叠式提醒设置。
   - 下次生成时间预览。
   - 失败重试和失败原因。

4. 样本回归
   - 建立支付文本 fixture。
   - 覆盖微信、支付宝、银行卡通知。
   - 敏感截图不入库，但 OCR 后文本 fixture 必须可测试。

5. 我的页版本变化简介
   - 在“我的”页新增“版本”区域，展示当前版本号，格式为 `0.3`、`0.3.1`，不带 `v` 前缀。
   - 展示“本版本变化简介”，用 2-4 条用户语言概括新增功能、体验改进和重要修复。
   - 提供“查看全部版本变化”入口，能回看 `0.2.1`、`0.2.2`、`0.3` 及后续版本变化。
   - 建立发布前版本检查：每次按照版本迭代规划执行时，必须同步更新 App 构建版本、我的页当前版本号和版本变化简介。

### 3.2 改进点

- 从“报告列表展示结果”升级为“报告详情可解释结果”。
- 从“报告重建”升级为“报告按周期更新”。
- 从“看洞察”升级为“洞察能回跳到相关记录”。
- 从少量手写测试升级到真实脱敏样本回归。
- 从设置页只放基础配置，升级为用户可回看本版本与历史版本变化。
- 从人工记忆版本号，升级为每次版本迭代都必须同步更新版本号和变化简介。

### 3.3 验收标准

- 报告重复生成不会丢失历史报告。
- 用户能解释报告来自哪些记录。
- 报告详情可跳转到对应明细筛选。
- 至少 20 条真实脱敏 fixture 通过解析回归。
- “我的”页显示当前版本号 `0.3`，不出现带 `v` 前缀的格式。
- “我的”页展示 `0.3` 的本版本变化简介，并可回看 `0.2.1`、`0.2.2` 的变化简介。
- 发布检查清单包含版本号更新项，后续版本按规划迭代时必须同步更新。

## 4. 0.4：规则学习与明细效率

周期：2-3 周  
主题：让系统越用越省心。  
版本目标：把用户修正变成规则，让明细查找和整理更高效。

### 4.1 功能迭代点

1. 规则管理
   - 展示商户关键词、分类、支付方式、命中次数。
   - 支持启用、禁用、编辑。
   - 标记系统生成规则和用户确认规则。

2. 低置信度复核
   - 风险字段标识。
   - 接受前快速修正。
   - 低置信度候选不可静默入账。

3. 明细搜索与导出
   - 关键词搜索。
   - 分类、支付方式、金额范围组合筛选。
   - CSV 导出。

4. 删除与修改安全性
   - 删除后支持撤销。
   - 批量操作前有明确确认。
   - 修改记录后刷新相关报告摘要。

### 4.2 改进点

- 从一次性人工修正，升级为可复用规则学习。
- 从普通列表，升级为可搜索、可筛选、可导出的账本。
- 从“删除即消失”，升级为有撤销和确认的安全操作。

### 4.3 验收标准

- 手动修正后的分类能影响下一次同商户候选。
- 低置信度字段不会无提示入账。
- 用户能在 10 秒内找到一笔历史消费。
- 导出的 CSV 字段完整且金额、日期格式稳定。

## 5. 0.5：Beta 准备

周期：2-4 周  
主题：准备真实长期使用。  
版本目标：补齐首次使用、数据迁移、备份恢复、发布稳定性。

### 5.1 功能迭代点

1. 首次使用引导
   - 解释导入、复核、报告、隐私边界。
   - 引导用户完成第一次导入或手动记账。

2. 数据迁移和备份
   - 本地模型迁移策略。
   - 导出和恢复入口。
   - 升级失败时的保护策略。

3. 稳定性与发布材料
   - Crash 处理。
   - App Store 截图和说明。
   - 50+ 条脱敏样本回归。

4. 隐私与权限收口
   - 统一权限说明。
   - 明确截图识别可能上传的数据范围。
   - 提供关闭相关能力后的替代路径。

### 5.2 改进点

- 从“能用”升级到“新用户知道怎么用”。
- 从“本地保存”升级到“升级和迁移有保护”。
- 从开发验证升级到发布前回归验证。

### 5.3 验收标准

- 新用户首次打开能完成一次导入或记账。
- 升级后旧数据可用。
- 主要路径无阻塞崩溃。
- 发布材料和隐私说明一致。

## 6. 当前实现风险清单

1. 导入页候选可见性仍是最高优先级风险。
   - 如果临时提示或当前批次状态隐藏全局待复核，分享扩展和快捷指令就会显得“导入了但找不到”。

2. 报告生成仍需要从“重建”转向“可信 upsert”。
   - 当前阶段可接受重建，但进入 0.3 前必须修正，否则历史报告和用户信任都会受损。

3. OCR 质量策略已经纠偏，但缺少样本回归。
   - 真实账单复杂度不能只靠少数单测保证，需要脱敏 fixture。

4. 写入副作用正在集中，但还没完全收口。
   - 任何新增、编辑、删除入口都要检查是否刷新报告和提醒。

5. UI 文案需要继续压缩技术感。
   - 用户要确认金额和商户，不要理解 Tencent、Vision、pipeline、batch 这些实现细节。

6. 版本号与版本变化简介容易被实现遗漏。
   - 后续每次按版本规划开发时，都必须把版本号更新和“我的”页版本变化简介纳入发布验收，且用户可见版本号不带 `v`。

## 7. 决策记录

- 接受 0.2.1 对总览减负的判断，后续不再把导入和报告塞回总览。
- 接受“导入”作为独立主流程，不再让分享扩展或快捷指令直接写账。
- 接受“报告”作为长期能力，但先修可信度，再扩图表。
- 接受 OCR 质量优先策略，同时用隐私文案而不是技术开关建立信任。
- 0.2.2 是稳定校准版，不做新功能扩张。
- 0.3 增加“我的”页版本变化简介，作为长期版本沟通入口；后续版本迭代必须同步更新用户可见版本号和变化简介。
